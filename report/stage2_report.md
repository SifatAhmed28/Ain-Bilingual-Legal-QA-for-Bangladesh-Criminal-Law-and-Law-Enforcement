### Pipeline

```
sections.jsonl
  -> clean_text()        HTML, page furniture, footnote markers, duplicate section no.
  -> normalize_text()    NFC, Bangla nukta recomposition, digits -> ASCII, danda -> ।
  -> detect_lang()       script ratio per section / sentence / clause
  -> split_all()         sentences (। . ? !) and clauses ((1), (a), provisos)
  -> tokenise            whitespace baseline + embedding-model subword
  -> bm25_text()         stopwords + light stemming (BM25 only)
  -> chunk_section()     1 section = 1 chunk; >400 tokens -> 400/50 overlap
```

## 1. Cleaning

**What.** Remove presentation artefacts that are not legal text: HTML entities/tags, page-number lines, repeated running heads, footnote markers, superscript footnote digits, `[* * *]` omission markers, and the section number that duplicates the `section_no` metadata.

**Why.** Footnote numbers and page furniture are corpus-specific noise: they inflate the vocabulary, create false BM25 matches (a query for `302` should match section 302, not footnote 302) and waste embedding tokens. The section number is kept once, in metadata, instead of being repeated at the head of every chunk.

**What is *not* removed.** Amendment brackets such as `[জুডিসিয়াল ম্যাজিস্ট্রেট]` are kept: the bracketed words are in force and are often the exact phrase a query uses. Only numeric-only brackets at the start of a section, and a footnote digit glued to an opening bracket (`3[or Police Commissioner]`), are markers and are removed.

**Result.**

| Rule | Hits |
| --- | --- |
| HTML entities (`&amp;`, `&nbsp;`) | 0 |
| HTML tags | 0 |
| Zero-width / invisible characters | 0 |
| Line-end hyphenation joins | 0 |
| Page-number lines | 0 |
| Page-number dashes (`- 12 -`) | 0 |
| Running-head lines | 0 |
| Duplicate section numbers | 2850 |
| Footnote markers (`[1]`, `3[`, superscripts) | 11 |
| Omission markers (`[* * *]`) | 201 |
| Sections with runs of >=2 spaces | 125 |

HTML, page and running-head counts are **0** in `sections.jsonl` because Stage 1 already stripped the markup and bdlaws' print HTML has no pagination furniture. The rules are still applied (and unit-tested on synthetic input) so that a different source cannot silently reintroduce them. On this run the rules that fire are: Duplicate section numbers (2,850), Footnote markers (`[1]`, `3[`, superscripts) (11), Omission markers (`[* * *]`) (201), Sections with runs of >=2 spaces (125).

## 2. Unicode normalisation

**What.** Apply NFC, then explicitly re-compose the three Bangla nukta letters (ড় ঢ় য়), unify the two danda characters (`৷` -> `।`), and convert Bengali digits to ASCII (`০১২৩৪৫৬৭৮৯` -> `0123456789`).

**Why NFC alone is not enough for Bangla.** U+09DC (ড়), U+09DD (ঢ়) and U+09DF (য়) are *composition-excluded*: NFC decomposes them into base + nukta (ড + ়, ড + ়, য + ়) instead of composing them. The corpus uses the pre-composed form almost everywhere, and so do Bangla keyboards. Normalising to the decomposed form would therefore rewrite thousands of characters and break exact matching against user queries. The pipeline runs NFC and then maps the decomposed sequences back to U+09DC/U+09DD/U+09DF, so all three spellings collapse to one code point. The same function is applied to queries.

**Digits.** Bengali digits are converted in the indexed text only; the original text stays in `sections.jsonl`. This lets a query for `ধারা ৩০২` match `section 302`, and lets section references be compared across languages. Dates and amounts are converted too, which is harmless for retrieval and keeps the tokenizer vocabulary smaller.

**Result.**

| Operation | Characters |
| --- | --- |
| Pre-composed nukta letters in input (ড় ঢ় য়) | 8816 |
| Decomposed nukta sequences in input | 1 |
| Split vowel signs composed by NFC (ো ৌ) | 32 |
| Nukta letters re-composed after NFC | 8817 |
| Bengali digits converted | 6740 |
| Danda variants unified (`৷` -> `।`) | 243 |
| Zero-width characters | 0 |

After the pipeline, `normalize_text` is idempotent on **2,970/2,970** section texts (100.0%), i.e. no residual variant forms remain.

Illustration of the variant-character rule (both inputs normalise to the same output):

```text
input A: ড়   (U+09DC, pre-composed)
input B: ড + ় (U+09A1 U+09BC, decomposed)
output : ড়   (U+09DC)
```

## 3. Language identification

**What.** Count Bangla letters (U+0980–09FF letter sub-ranges) and Latin letters in a segment; label `bn` when the Bangla share is >=85%, `en` when it is <=15%, otherwise `mixed`. Segments with no letters (e.g. `(1)`, `1973`) inherit the parent's label and are flagged `lang_inherited`.

**Why.** The corpus is effectively two monolingual sub-corpora, but legal Bangla routinely embeds English terms (`এজাহার (FIR)`, `চার্জশিট`) and English sections cite Bangla-free Latin abbreviations. A per-segment label lets Stage 3 route queries and choose a language-specific analyzer, and it quantifies code-switching. The 85% threshold is deliberately conservative: a lower threshold labels an English section with one Bangla gloss as `mixed`.

**Result.**

| Label | Sections | Sentences |
| --- | --- | --- |
| bn | 1035 | 2542 |
| en | 1892 | 3292 |
| mixed | 43 | 111 |

- Code-mixed sentences (both scripts inside one sentence): **106** (1.8% of sentences).
- Sections whose text language differs from the Stage 1 `lang` field: **43** (Stage 1 used `mixed` for 'both translations present', which is a different concept).
- Known limitation: romanised Bangla (`naraji`, `jamin`) contains only Latin letters and is labelled `en`. This is handled at query time by the colloquial forms in the legal lexicon, not by the script detector.

## 4. Sentence and clause segmentation

**What.** Split on the Bangla danda `।` (and `৷`), `?`, `!`, and on English `.` when followed by whitespace and a capital letter, digit or Bangla letter. Abbreviations (`No.`, `Sec.`, `s.`, `i.e.`, `U.S.`, `Cr.P.C.`) and decimals are protected before splitting. Clauses are then split on sub-section markers `(1)`, `(2)`, `(a)`, `(b)`, `(ক)`, `(খ)` and on proviso/explanation cues (`Provided that`, `তবে শর্ত থাকে যে`, `Explanation`, `ব্যাখ্যা`).

**Why.** Sentences are the natural unit for overlap and for sentence-level citation. Clauses matter more in statutes than in prose: a proviso can reverse the rule in the main clause, and `(2)` can be the only thing that distinguishes two otherwise identical provisions. Keeping the marker attached to the clause text is therefore a hard requirement; a chunk that starts mid-section must still read `(2) ...`, not `...`.

## 5. Tokenisation: whitespace vs subword

**What.** Compare `text.split()` (whitespace) with the embedding model's subword tokenizer. Counts are computed per section and aggregated by language.

**Why.** Chunk size and cost are measured in *subword* tokens, not words. Bangla is agglutinative and the multilingual tokenizer has far less Bangla in its vocabulary than English, so the same legal content can cost two to three times as many tokens. The comparison sets the chunk budget and predicts the cost of the Bangla half of the corpus.

**A Bangla-specific pitfall.** `re.findall(r"\w+", "বাংলা")` returns four single-letter tokens because Bangla combining marks are not `\w`. The pipeline therefore splits on whitespace and trims edge punctuation, which keeps conjuncts intact.

**Result.**

| Lang | Sections | Words | Whitespace | Subword | Sub/word | Sub/100 chars |
| --- | --- | --- | --- | --- | --- | --- |
| en | 1,892 | 216,621 | 216,756 | 296,007 | 1.37 | 23.7 |
| bn | 1,035 | 122,350 | 122,586 | 269,652 | 2.20 | 33.0 |
| all | 2,970 | 343,092 | 343,472 | 574,762 | 1.68 | 27.5 |

Overall, the subword tokenizer produces **1.67x** more tokens than whitespace splitting. For Bangla the ratio is **2.20x**, versus **1.37x** for English.

## 6. Stopwords and stemming (BM25 only)

**What.** For the BM25 view only: remove a 160-word Bangla stopword list and a small English function-word list, then apply a light suffix stemmer (Bangla) and plural-only normalisation (English). Dense embeddings receive the normalised text with stopwords intact.

**Why.** BM25 is a lexical matcher: frequent function words such as `এই`, `এবং`, `যে`, `of`, `the` add no discriminative power and lengthen every document, which dilutes the score. Inflection is a real problem in Bangla (`আইনের`, `আইনকে`, `আইনে` all refer to `আইন`), so a light stemmer improves recall. Dense models already handle both phenomena in context, and removing stopwords there can delete legally meaningful negation (`না`, `নহে`, `not`), so the two views are deliberately different.

The Bangla stemmer is intentionally shallow: single-character suffixes such as `য়` and `র` are **not** stripped, because doing so turns `বিষয়` into `বিষ` and `ঘর` into `ঘ`. Longest-suffix-first ordering and a three-character minimum keep it safe. English uses plural-only normalisation; Porter-style stemming would conflate `conviction` and `convict`, which are legally distinct.

## 7. Chunking

**What.** One section is one chunk. A section longer than 400 subword tokens (including its citation header) is split on sentence boundaries into chunks of at most 400 tokens with about 50 tokens of overlap. Every chunk keeps `sec_uid` and gets `chunk_id = {sec_uid}#cNN`. A sentence that alone exceeds the budget is split on word boundaries; a clause is never cut without its marker.

**Why.** Section-level chunks preserve the legal unit of meaning and make citation exact. The 400/50 budget keeps chunks inside the embedding model's context window, and overlap protects a provision that straddles a boundary. Splitting on sentences rather than a fixed character window avoids chunks that begin mid-clause.

## 8. Legal dictionary and query expansion

**What.** A hand-built lexicon of **80** concepts with formal English, formal Bangla and colloquial/romanised forms (589 surface forms in total), cross-links between concepts, and 49 statute references (validated against `sec_uid`). Query expansion matches the longest surface form, ignores overlaps, and adds cross-lingual synonyms plus a few related concepts.

**Why.** Users do not speak in statute language. They write `jamin`, `naraji`, `rimand`, `amaljoggo` or `এজাহার`, while the corpus says `জামিন`, `নারাজি`, `পুনঃসমর্পণ`, `আমলযোগ্য` or `FIR`. Expansion bridges the three registers and the two scripts, and the statute links give Stage 3 an exact-section fallback when lexical matching fails. Expansion is kept small and is meant to be weighted below the original query terms, so it improves recall without hijacking the query.

## 10. Validation and limitations

Checks run at the end of the pipeline:
- Every section with text produced at least one chunk.
- Every chunk has a non-empty `sec_uid`; chunk ids are unique.
- No chunk exceeds the configured subword-token budget.
- Every overlap region is a suffix of the previous chunk body.
- `normalize_text` is idempotent on every section.
- All statute references in the lexicon resolve to a real `sec_uid`.
- Unit tests cover footnote stripping, nukta equivalence, digit unification, language ID, sentence/clause splitting, chunk budgets and query expansion (`python -m pytest tests/test_stage2.py`).

Known limitations:

- **Script detection is not language detection.** Romanised Bangla is labelled `en`; the lexicon compensates at query time.
- **No parallel translations.** Only 38 act titles are officially bilingual, so the EN/BN token comparison is exact for titles and aggregate (not sentence-aligned) for the rest.
- **The tokenizer is provisional.** It is the Stage 3 embedding model's tokenizer; if Stage 3 chooses a different model, chunk sizes must be recomputed with `--tokenizer-model`.
- **Page/header rules are defensive.** They fire on synthetic input and on other sources, not on the current bdlaws extract.
- **Light stemming is not morphological analysis.** It is tuned for BM25 recall, not for linguistic correctness.
